# Workspace Guidelines & Rules (Logistics TMS Fullstack)

## Architecture Overview
- **Backend**: NestJS 11+ located in [`backend/`](file:///d:/Projects/logistics-website/backend) (PostgreSQL on Neon, TypeORM, Custom JWT Auth, Swagger) — **Independent Git Submodule** (`logistics-website-backend`).
- **Frontend**: Next.js 15+ located in [`frontend/`](file:///d:/Projects/logistics-website/frontend) (App Router, React 19, Tailwind CSS, TanStack Query, Zustand) — **Independent Git Submodule** (`logistics-website-frontend`).
- **Git Submodules Rule**: Root repo (`logistics-website`), `backend/`, and `frontend/` are 3 independent Git repositories. When creating a feature branch or committing code, you MUST create branches and commit **directly inside the corresponding submodule** (`backend/` and/or `frontend/`), never only at the root repository.
- **Mandatory Project Repo Tracking on Task Start Rule**: Whenever starting any task, session, or feature implementation, `/leader` and all operating agents MUST ALWAYS activate and run tracking commands across all 3 project repositories (`root`, `backend/`, `frontend/`) before planning, dispatching, or modifying code:
  - Run status check: `npm run repo:status` (or `git status -sb; git -C backend status -sb; git -C frontend status -sb`)
  - Run branch tracking check: `npm run repo:tracking` (or `git branch -vv; git -C backend branch -vv; git -C frontend branch -vv`)
  This guarantees: (1) Active branch alignment across root and submodules (prevents committing to `main`/`dev` or detached HEAD), (2) Upstream tracking synchronization (`[ahead N, behind M]`), and (3) Immediate detection of uncommitted/dirty working trees before changes occur.
- **Feature Branch Base Branch & Quality Gate Promotion Mandate (Base from `dev` Rule)**:
  - **Mandatory Base Branch**: All feature branches (`feature/<scope>-<name>`) and bugfix branches (`fix/<scope>-<name>`) MUST ALWAYS branch off from `dev` (after running `git checkout dev && git pull origin dev` inside target submodules and root). NEVER branch off directly from `master` (except for emergency production `hotfix/<name>` branches).
  - **Strict 3-Stage Promotion Pipeline**:
    1. **Develop on Feature Branch**: Implement, commit directly inside target submodule (`backend/` and/or `frontend/`), and push feature branch to remote.
    2. **Merge to `dev` & E2E Automated Verification**: Merge feature branch into `dev`, push to `origin/dev`, and wait for deployment `READY` on **Domain Dev**. Execute automated Playwright E2E suites against Dev environment.
    3. **Promote to `master` (Production-Ready Gate)**: ONLY after 100% of E2E verification tests PASS on `dev`, checkout `master`, pull `origin/master`, merge `dev` into `master`, and push to `origin/master` (strictly submodule-first: `backend/`, `frontend/`, then `root`).

## Safety & Governance Rules (STRICT)
- **Language Policy**: Skill and agent guideline documentation MUST be written in English to minimize token consumption and maximize context efficiency.
- **Secrets & Security**: NEVER commit/push `.env` files or credentials. Ensure secrets stay in `.env` (git-ignored).
- **MCP Config Files**: NEVER commit/push any MCP (Model Context Protocol) config files — these often contain API keys. Blocked patterns: `mcp.json`, `.mcp/`, `mcp_config.json`, `claude_desktop_config.json`, `.cursor/mcp.json`, `.gemini/mcp*.json`, `windsurf_mcp.json`, `codeium_mcp.json`, or any JSON/YAML with `"mcpServers"` key containing credentials.
- **DB Destructive Ops**: NEVER run `DROP DATABASE`, `DROP TABLE`, `TRUNCATE`, or `schema sync` (synchronize: true).
- **Schema & Migrations**: BEFORE modifying, renaming, or dropping existing DB columns/entities, analyze data impact, notify the user, and get explicit approval before generating/running migrations.
- **Git Safety**: NEVER run `git push --force` or push code without explicit user request.
- **Codebase Integrity**: DO NOT delete critical source folders or bypass error checks with silent fallbacks.
- **Frontend Error Sanitization Rule**: NEVER render raw technical error keys/codes (e.g., `incorrectEmailOrPassword`, `notFound`, `emailNotExists`, camelCase identifiers, raw DTO constraint dumps) directly to users. Error handling MUST use `formatApiError()` in `@/lib/api-error`, prioritize localized user-facing API messages (`errorData.message`), and map technical codes to clear Vietnamese messages.
- **Zero Technical/Document Jargon in UI Rule (Operational Terminology Mandate)**: All UI screens, vector `.pen` canvas designs, frontend components, and user-facing badges MUST strictly eliminate internal technical/document jargon, developer task prompts, and internal spec labels. They MUST be replaced with natural, professional Vietnamese logistics warehouse operational terminology (`thuật ngữ vận hành kho bãi thực tế`).
  - **Strictly Prohibited in UI**: Spec abbreviations or technical notes such as `Quy chuẩn kiện vận tải (No-SKU)`, `(First-mile Inbound)`, `(Middle-mile Transfer)`, `(Last-mile Outbound)`, `Consignment Level`, `Đang xuất nhỏ giọt` (use `Đang xuất từng phần`), task codes (`TASK-ORD-...`), or database schema names.
  - **Operational Logistics Equivalents**: Use standard operational Vietnamese: `Tiến trình vận chuyển & Tồn kho`, `1. Xe nhập kho`, `2. Trung chuyển liên Hub`, `3. Xe xuất kho`, `Tổng nhập`, `Đã xuất`, `Tồn khả dụng`, `Xuất hoàn tất`, `Hàng luân chuyển`.
  - **Detail vs. Create Mode Strict Separation**: Detail / Inspection dialogs (`WarehouseWaybillDetailModal`, Sheet drawers) are strictly read-only audit views. NEVER render creation tabs (`Mới hoàn toàn` / `Luân chuyển nội bộ`), receipt form inputs (license plate, driver picker), or editable grids inside read-only inspection dialogs.
- **Zero Redundant Icons Rule (Button & Label Cleanliness)**: In both vector design (`.pen` canvas) and frontend code (React / Next.js / Tailwind / Shadcn UI), NEVER combine a vector icon element/component with a duplicate emoji or symbol (e.g., `+`, `🚚`, `📦`, `🔄`, `🖨️`, `✕`, `🔍`) inside the text label. Use EITHER a vector icon OR clean text label, never duplicate them (e.g. use `<Button><IconPlus /> Tạo đơn mới</Button>`, NEVER `<Button><IconPlus /> + Tạo đơn mới</Button>` or `<Button><IconTruck /> 🚚 Luân chuyển</Button>`).
- **Dynamic Counters & Metric Integrity Rule (Zero Arbitrary Numbers)**: Every number displayed in the UI (KPI Stat Cards, tab counts, badges, table summaries, cargo volumes, weights, package counts) is a state-driven business metric and MUST be backed by end-to-end backend queries and dynamic reactive state. NEVER hardcode placeholder numbers or use falsy fallbacks (`|| 52` masks `0` with `52`; use `?? 0`). If any counter formula, lifecycle mapping, or filter parity is unclear, MUST clarify with the User immediately.
- **Real Database Data Mandate (Zero Mock Data Rule)**: The entire Logistics TMS system is fully integrated and operates on REAL PostgreSQL DB data. ALL UI components, tables, filters, dropdowns, KPI cards, and operational workflows MUST communicate directly with real backend REST endpoints. NEVER use mock data, hardcoded sample arrays, fake fallback rows in `.catch()` blocks, or fake initial state data. When an API returns empty or errors out, render proper empty states or sanitized user-facing error toasts.
- **Pencil Design-to-Code Translation Fidelity Rule**: When translating `.pen` vector designs into React/Next.js/Tailwind components, agents MUST strictly follow the **Translation Protocol** in [`nextjs-best-practices`](file:///d:/Projects/logistics-website/.agents/skills/nextjs-best-practices/SKILL.md). NEVER default to a generic `<table>` when `.pen` defines Card Lists (`trip_modal_dialog_card`), preserve modal overlays with backdrops (`[MODAL_STEP_X]`), keep selection accent bars (`border-l-4 border-l-blue-600`), and verify visual match with Playwright screenshots via [`visual-pen-matcher`](file:///d:/Projects/logistics-website/.agents/skills/visual-pen-matcher/SKILL.md).
- **UI Compact Density & Narrow Spacing Mandate (Quy chuẩn giao diện hẹp & triệt tiêu khoảng cách thừa)**: To maximize information density for high-tempo warehouse and dispatch operations (zero wasted whitespace, maximum visible items per screen), all UI screens, cards, modals, grids, and components MUST strictly enforce compact spacing:
  - **Strictly Banned Oversized Classes (NGHIÊM CẤM TUYỆT ĐỐI SINH CODE)**: `p-4`, `p-5`, `p-6`, `p-8`, `px-4`, `px-6`, `py-3.5`, `py-4`, `py-6`, `space-y-3`, `space-y-3.5`, `space-y-4`, `space-y-6`, `gap-3`, `gap-3.5`, `gap-4`, `gap-6`. Generating these classes in operational screens is an automatic code quality FAIL.
  - **Base Card Padding (4px)**: Thẻ `<Card />` và `<CardContent />` mặc định padding siêu gọn `4px` (`[--card-spacing:--spacing(1)]` trong [`card.tsx`](file:///d:/Projects/logistics-website/frontend/src/components/ui/card.tsx) hoặc `p-1`, `py-0`). NEVER use `p-4` or larger for operational cards.
  - **Modal / Dialog Spacing & Content-Driven Width Mandate (Quy chuẩn suy luận độ rộng Modal theo nội dung)**: Modal Body strictly uses `p-2` (max `p-2.5`, 8-10px) with `overflow-y-auto max-h-[85vh]` for internal compact density. HOWEVER, the outer modal container width MUST dynamically adapt to UI content complexity (triệt tiêu tình trạng bóp nghẹt bảng dữ liệu / zero squished tables):
    - *Data Tables (>= 5 cols), Tally Sheets, Stored Order Selection, Waybill/Trip Inspection*: MUST use wide layouts (`w-[92vw] sm:max-w-5xl xl:max-w-6xl` or `w-[96vw] max-w-7xl`, Pencil width 1100px - 1440px). NEVER squeeze tables into `max-w-sm` or `max-w-xl`.
    - *2-Column Forms / Master-Detail (>= 8 inputs)*: Use `sm:max-w-3xl` to `max-w-4xl` (Pencil width 800px - 920px).
    - *1-Column Forms (3-6 inputs)*: Use `sm:max-w-xl` to `max-w-2xl` (Pencil width 560px - 660px).
    - *Simple Action Alerts / Deletion Confirmation*: Use `sm:max-w-md` (Pencil width 420px - 480px).
  - **Tight Element Gaps**: Gaps between sections/cards MUST NOT exceed `8px` (strictly use `gap-1.5` to `gap-2`, `space-y-1.5` to `space-y-2`, NEVER `gap-3`, `gap-4` or `space-y-3`, `space-y-4`). Input grid gaps: `gap-1.5` to `gap-2`. Label margin: `mb-1` (4px). Input/Button height: `h-8` to `h-8.5`.
  - **Compact Typography Scale (Tối đa hóa số lượng item)**: To maximize the number of visible items on screen at once, font sizes and row heights are strictly minimized: Table data cells (STT, kiện, kg, m³, notes, dates, addresses) = `text-[10px]`; table headers & badges = `text-[10px]`; order/trip codes = `text-[11px] font-mono font-bold`; table row padding = `py-1 px-1.5` (dropping row height to ~26px to double visible rows); Card base font = `text-xs`.
  - **Cohesive & Sticky Layout**: Interrelated operational blocks (e.g., Vehicle reception info and cargo table) must be tightly bonded together (`gap-2` / `space-y-1.5`). Action buttons (Save draft, Preview, Confirm receipt, Print) MUST be pinned with `sticky bottom-0 bg-white/dark:bg-slate-900 border-t p-1.5` so warehouse operators never scroll to find action triggers. Table headers MUST be `sticky top-0`.
  - Detailed spec & banned class table: See [`.agents/rules/ui-compact-density.md`](file:///d:/Projects/logistics-website/.agents/rules/ui-compact-density.md).
- **RBAC Compliance**: Before adding/modifying any endpoint or menu, MUST reference [`rbac-matrix.md`](file:///d:/Projects/logistics-website/.agents/rules/rbac-matrix.md) — the system's authoritative permission matrix. Ensure all 3 layers are updated: Sidebar UI, Route Guard, API Guard.
- **Network & Health Check Execution Protocol (Anti-Hang / Anti-Stuck Mandate)**:
  - When inspecting, pinging, or health-checking remote services (`domain dev`, `domain pro`, Render, Vercel, external APIs) from CLI, scripts, or agent commands, **NEVER run bare `curl` without a timeout or without `.exe`** in PowerShell. In Windows PowerShell, `curl` aliases to `Invoke-WebRequest` without default timeouts, causing the terminal process to hang indefinitely when a cloud backend (e.g. Render Free Tier) is sleeping (cold start 45-60s) or rebuilding/deploying.
  - **Strict CLI Mandates**:
    - Always use explicit `curl.exe` with a bounded timeout (`-m 15` or `--max-time 15`) and visible status header (`-i` or `-sS -i`): `curl.exe -m 15 -i https://<domain>/api/v1/health`. NEVER use bare `curl -s <url>`.
    - In native PowerShell, always set `-TimeoutSec`: `(Invoke-WebRequest -Uri "https://<domain>/api/v1/health" -TimeoutSec 15).Content`.
    - In Node.js / Playwright / scripts, always supply an abort signal: `fetch(url, { signal: AbortSignal.timeout(15000) })`.
    - Polling checks MUST NEVER loop indefinitely; cap polling at maximum 5 attempts with 15–20s backoff.
- **Zero Premature Telegram Reporting Mandate (Quy chuẩn Chống Báo Cáo Nghiệm Thu Non & Cưỡng Chế Dev E2E Gate)**:
  - Operating agents and background daemons (`neon-worker.mjs`) are STRICTLY FORBIDDEN from reporting task completion to Telegram or claiming "ĐÃ TEST DEV XONG" immediately upon Git push or local compile exit.
  - A completion notification is ONLY permitted after fulfilling the full 5-stage closed verification pipeline:
    1. **Submodule Git Push to `dev`** (`backend/`, `frontend/`, `root`).
    2. **Cloud Deployment Readiness Wait**: Wait 45–60s for GitHub webhooks to trigger builds on Vercel & Render; poll Backend Dev Health (`/api/v1/health`) and Frontend Dev URL until responsive.
    3. **Automated Playwright E2E Verification on Dev & Autonomous Self-Healing Retry (Max 3 Attempts)**: Execute the target test suite (`npx playwright test e2e/<spec> --project=chromium`) directly against live Dev endpoints (`PLAYWRIGHT_BASE_URL` & `API_URL`). If a failure occurs, the system initiates an autonomous RCA & fix loop (up to 3 retries) where AI analyzes the error, modifies code, rebuilds, pushes to `dev`, waits for redeployment, and re-tests.
    4. **Cross-Evaluation Audit**: Validate the test suite with `node scripts/e2e-auditor.mjs` (score ≥ 40/50, 0 FAIL).
    5. **Visual Evidence Verification**: Capture and attach real screenshot proof (`screenshot_*_verified.png`) uploaded directly via Telegram `sendPhoto`.
  - If any E2E test continues to fail after exceeding 3 retries or deployment times out, only then MUST the task be flagged as `FAILED` (`DEV_E2E_FAILED`), alerting the team on Telegram with exact Playwright error traces and retry history, and never marked as `COMPLETED`.
- **System Evolutionary Timeline & Technical Memory Mandate ("Biên Niên Sử & Ký Ức Kỹ Thuật Bất Biến")**:
  - Whenever completing any feedback, bug fix, or major architectural feature, operating agents MUST record technical documentation via `npm run todo:record <folder>` to generate [`RESOLUTION.md`](file:///d:/Projects/logistics-website/docs/SYSTEM_TIMELINE.md) and update [`docs/SYSTEM_TIMELINE.md`](file:///d:/Projects/logistics-website/docs/SYSTEM_TIMELINE.md).
  - When starting a new session or onboarding to unfamiliar modules, all AI agents MUST read `docs/SYSTEM_TIMELINE.md` and `CODEBASE_AUDIT.md` to establish context on existing capabilities, design decisions, and proven operational invariants.
